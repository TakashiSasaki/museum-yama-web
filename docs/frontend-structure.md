# フロントエンド構造と設計方針

このリポジトリは、以下の2つの異なる利用文脈を持つフロントエンドアプリケーションが同居する構造になっています。

## 1. 2つのフロントエンドの役割

### スマートフォン向け 2D フロントエンド (`/explore` など)
- **ターゲット**: スマートフォンユーザー
- **利用文脈**: ユーザーが自身のスマートフォンで山を探し、市町村・おすすめ・山名検索・現在地などの機能を使って目的の山を見つけ、必要に応じてYAMAPなどの外部アプリへ遷移する。
- **技術スタック/UI**: 2D Google Map (`@vis.gl/react-google-maps`) ベース。モバイルに適したドロワー、サイドバー、検索UI、画面遷移を持つ。

### 展示・サイネージ向け 3D フロントエンド (`/earth`)
- **ターゲット**: 愛媛大学ミュージアム等の展示空間の来館者
- **利用文脈**: 来館者が横型タッチディスプレイを操作しながら、愛媛県の山や地形を視覚的・直感的に体験する。
- **技術スタック/UI**: 3D 地形表示フロントエンド。自動回転、3Dカメラ制御、タッチ操作説明、長押しでの診断HUDなど、展示・サイネージ用の特殊なUIと制御を持つ。長時間の稼働を前提とした低FPS・解像度スケールなどのパフォーマンス調整が含まれる。

## 2. 共通化に関する設計方針（重要）

2D と 3D のフロントエンドは、「用途」「画面サイズ」「操作体系」「性能要件」が大きく異なります。そのため、**UI・状態管理・操作体系・カメラ制御・パフォーマンス制御は安易に共通化しないでください。** 

将来の開発者やコーディングエージェントが、2D と 3D のコードに重複や類似性を見つけたとしても、無条件にコンポーネント化や共通化を行わないように強く注意してください。

### 共通化してよいもの（基礎データと純粋な処理）
原則として、共通化の対象は「基礎データ層」と「純粋なデータ処理」に限ります。
- `mountain_all.json` などの基礎データファイル
- 山データの型定義 (TypeScript Interfaces/Types)
- 緯度経度を持つ山だけを抽出・フィルタリングする純粋なユーティリティ関数
- 難易度ランクの意味や定義
- YAMAPへのリンクURL生成などのフォーマット処理

### 共通化しない方がよいもの（UIと制御層）
それぞれの利用文脈に合わせて完全に分離して実装・維持してください。
- 2DマップのモバイルUI と 3DマップのサイネージUI
- マーカーやピンの表示デザイン（HTMLマーカーか、3D空間上のオブジェクトか）
- 検索UI、ボトムドロワー、サイドバーの実装
- 自動回転、タッチパネル用HUDなどの特殊機能
- カメラ操作や地図の移動制御
- パフォーマンス最適化のロジック

## 3. 変更時の注意点

- **2D側の変更**: モバイルでのUX（操作性、画面領域の制約、パフォーマンス）への影響を常に確認してください。
- **3D側の変更**: 展示・サイネージ運用（タッチパネルでの操作性、長時間の安定稼働、自動再生への復帰など）への影響を確認してください。
- **基礎データ（`mountain_all.json` など）の変更**: 基礎データを変更・更新する場合、2D と 3D の両方の表示や機能に影響が及ぶ可能性があることを考慮し、双方での動作確認を行うようにしてください。
